> Native GPU-accelerated engine for generating and editing fantasy worlds. Rewritten from scratch as an original open-source product, based on the procedural logic of **Azgaar's Fantasy Map Generator** (MIT) but with its own architecture, renderer and data format.

## Executive summary

Azgaar's Fantasy Map Generator is a web app (JS/TS) that generates and edits fantasy maps procedurally: terrain, rivers, climate, biomes, cultures, states, religions, routes, economy and military, all over a Voronoi mesh. It is open source (MIT), but limited by its SVG+DOM renderer, which does not scale well on large maps (confirmed by the community itself: an Electron port attempt was abandoned because it did not solve the real bottleneck).

This project is **not a port nor a wrapper of Azgaar**. It is a native engine (Rust + wgpu) that:
1. Can **import** data generated by Azgaar (`.map` / JSON export).
2. Converts that data to its own **GPU-optimized binary format** (`.vorn`).
3. Renders with real hardware acceleration (not SVG/DOM).
4. Eventually **reimplements and expands** all of Azgaar's procedural logic natively, to stop depending on Azgaar entirely.
5. Stays **open source**, with correct attribution to Azgaar for the reference logic/algorithms.

A key finding of this research (§3) changes the technical approach of the parser: **Azgaar's `.map`/JSON does not store the map geometry** (cell positions, neighbors, vertices) — it regenerates it on every load from a seed. This means "reading an Azgaar map" is not a passive parse: it requires **reimplementing the grid and Voronoi/Delaunay generation algorithm bit-exactly** so that the stored data (height, biome, culture, etc., indexed by cell) matches the correct geometry.

## 1. Vision and goals

### 1.1 Summary

Build a native, fast, extensible fantasy world engine — inspired by Azgaar but not limited by its 2017 technical decisions (SVG, DOM, single-threaded JS) — that can grow into a full **World Engine**, open to external integrations.

### 1.2 Goals

- [ ] Render maps of tens/hundreds of thousands of cells at 60 FPS with smooth pan/zoom.
- [ ] Read existing Azgaar maps (`.map` and JSON export) with geometric fidelity.
- [ ] Define a binary format (`.vorn`) as the internal source of truth, fast to save/load.
- [ ] Reimplement (progressively) all of Azgaar's procedural logic in Rust.
- [ ] Offer interactive editing (terrain, entities, borders) with real undo/redo.
- [ ] Expand capabilities beyond what Azgaar allows today (see §21).
- [ ] Keep the project open source, with correct attribution.

### 1.3 Project name: Voronia

The candidates evaluated in the first version of this document (`worldforge`, `terraforge`, `mapsmith`, etc.) were discarded after checking real collisions:

| Discarded candidate | Why |
|---|---|
| `Worldforge` | Strong collision: an active open-source MMORPG framework since 1998 (worldforge.org, Ogre3D engine), a worldbuilding wiki for writers (worldforge.me) and a worldbuilding tool on itch.io — all three use the name almost literally. |
| `Terraforge` | Collides with **TerraForge3D**, a real open-source procedural terrain generation tool (alternative to World Machine/Gaea). Exactly the same product space. |
| `Tessera` (evaluated as alternative) | Collides with a widely used Unity asset (Tessera Procedural Tile Generator), an academic WFC paper with the same name, and a game engine called "Tessera Engine" released in 2026. |
| `Graticule` (evaluated as alternative) | A real cartographic term, and already used by half a dozen software products (geocoding, GIS, a health-data company). Too saturated. |

**Chosen name: `Voronia`.**

- Verified with no direct collisions as a software/project name (specific searches returned no product, library or repo with that exact name).
- A genuinely original name, not an obvious English compound (avoids the root problem: "World/Terra/Map + Forge/Craft/Smith" is the first idea everyone has in this field, which is why it collides so much).
- Intentional double reading: for anyone familiar with the domain, it points straight to **Voronoi**, the geometric diagram that is the heart of the world mesh (§7.1) — coherent with the name at the deepest level of the architecture. For anyone else, it simply sounds like a fantasy toponym (same pattern as Narnia, Sonoria, etc.), fitting for the fantasy map domain.
- Short, easy to pronounce in Spanish and English, a good crate (`voronia`) and repo name candidate.

Fallback alternative if it ever stops convincing: `Mundrift` (name invented from scratch, no hits in the searches performed — more neutral, less loaded with technical meaning).

> Honest note: no web search is 100% exhaustive as a trademark check. Before registering the repo on GitHub and publishing the first crate on crates.io, a final availability check on those two specific platforms is worthwhile (two minutes, zero friction, closes any residual doubt).

### 1.4 Non-goals (out of v1 scope)

- Not a 1:1 pixel-perfect clone of Azgaar's UI.
- No retroactive binary compatibility with **all** historical `.map` versions (only the current JSON/`.map` format; very old versions are out unless explicitly requested).
- No multiplayer/real-time collaboration in v1 (remains an extension, §21).
- No mobile/tablet target in v1 (desktop Linux/Windows/Mac).
- Armoria (shield generator) and Watabou's Medieval Fantasy City Generator are not reimplemented — listed as optional external integrations (§21).

### 1.5 Target audience and use cases

- hanserlodev's personal use for worldbuilding.
- Worldbuilding community, TTRPG DMs, fantasy writers — same audience as Azgaar.
- Potential technical audience: people who want an embeddable world engine for their own games/tools.

## 2. Relationship with Azgaar's Fantasy Map Generator

### 2.1 What is reused

- **The reference concepts and algorithms** that Azgaar itself cites as inspiration (see §28): Martin O'Leary's terrain generation, Amit Patel's polygonal map generation (Voronoi/Delaunay), and Scott Turner's approach ("Here Dragons Abound").
- **The conceptual data model** (grid/pack, cells, features, cultures, states, burgs, religions, rivers, routes, zones, biomes, namebases) — described precisely in §7, taken from Azgaar's official wiki.
- **Input compatibility**: the ability to import maps already generated in Azgaar.

### 2.2 What is rewritten entirely

- All the code: 0% of Azgaar's JS/TS is reused literally. It is reimplemented in Rust from scratch.
- The renderer: from SVG/DOM to a GPU pipeline (wgpu).
- The internal persistence format: from `.map` (custom text + embedded SVG) to `.vorn` (own binary).
- The UI: from HTML/CSS to an immediate-mode native UI (egui, see §12).

### 2.3 License and attribution

- Azgaar's Fantasy Map Generator is **MIT licensed** (copyright Max Haniyeu / Azgaar, 2017–2024). The project itself clarifies that maps, screenshots and derivative works generated *with* the tool are not restricted by the license and can be used commercially — but that applies to *generated maps*, not the source code itself.
- MIT allows reimplementing, adapting and redistributing with the only condition of keeping the copyright and license notice if literal code is reused. Since **no code is copied** here, but algorithms/logic are reimplemented from scratch, there is no legal license obligation — but **explicit attribution is correct and honest**.
- Concrete action: Voronia's `README.md` must include a "Credits and inspirations" section mentioning Azgaar, with a link to the original repo and the three reference articles (§28). This is also simply good open-source community practice.
- Voronia will also be licensed under **MIT** (recommended): maximum compatibility, zero friction for adoption, coherent with the ecosystem it comes from.

### 2.4 Data compatibility

- Azgaar's own team states in its contribution guide that the **future** architecture they are migrating to separates **world data**, **procedural generation**, **interactive editing** and **rendering** into 4 layers: `world data (state)` → `generators (model)` → `editors (controllers)` → `renderer (view)`, with flow `settings → generators → world data → renderer` and `UI → editors → world data → renderer`.
- This **directly validates** Voronia's architecture (§5): we are not inventing an arbitrary separation; we are going one step beyond where Azgaar itself wants to evolve, but on a native platform.

## 3. ⚠️ Critical finding: how Azgaar's format actually works

This is the most important thing to internalize before writing a single line of parser.

According to the official Azgaar data model documentation:

- Azgaar keeps two main objects: **`grid`** (base mesh, before "repacking") and **`pack`** (final mesh, optimized for the current landmass, after "repacking").
- Both contain **Voronoi data**: point/cell positions, neighbors, vertices.
- **This geometric data is NOT saved in the `.map` nor in the JSON export.** It only lives in memory during the session and is **recomputed every time a map is loaded.**
- What IS saved are the **per-cell attributes** (height, biome, culture, state, population, river, flux, etc.), indexed by a **cell index number** — not by coordinates.

### 3.1 Direct technical implication

For a saved attribute array (e.g. `pack.cells.h` = heights) to make sense when loaded, **cell `N` must fall exactly in the same geographic position it had when Azgaar generated and saved that map.** That is only possible if:

1. The **seed** and parameters (`cellsDesired`, canvas dimensions, `spacing`) used in the original generation are known.
2. The same algorithm is reimplemented **bit-exactly**, covering:
   - Seeded pseudo-random generator (to be determined in Phase 0 which one Azgaar uses internally).
   - Jittered square grid point placement.
   - Delaunay triangulation over those points.
   - Voronoi diagram derivation (dual of the Delaunay).
   - The "repacking" process (grid → pack): how the mesh is trimmed/optimized to the real landmass.

If any of these steps differs even slightly from the original, **cell indices will not match**, and loading a real `.map` will produce a map with misplaced attributes (mountains where there should be sea, etc.).

### 3.2 What this means for the roadmap

- **Phase 1 is not "write a JSON parser".** It is "port Azgaar's grid + Delaunay/Voronoi + repacking generator to Rust with the same deterministic behavior", and **only then** parse/apply the attribute arrays over that regenerated geometry.
- This is researched in depth in **Phase 0** (reviewing Azgaar's real source — `src/` folder of the repo — to identify the exact PRNG and repacking algorithm).
- Good news: this is exactly the kind of logic we also **want** to reimplement natively to generate new maps (not just import existing ones), so it is not "wasted" work — it is the heart of the generation engine (§10).
- Risk mitigation: if in Phase 0 the bit-exact replica proves unviable or too fragile (e.g. it changes between Azgaar versions), plan B is to support the **Full JSON export** (which includes more context than the legacy `.map`) as the only officially supported import path, clearly documenting that geometric fidelity depends on the Azgaar version used to export.

## 4. Design principles

1. **Data commands, rendering obeys.** The renderer never modifies world state; it only visualizes it (the same principle Azgaar already pursues in its future architecture).
2. **Everything is deterministic and reproducible.** Same seed + same parameters = same world, always. This enables testing, version comparison, and import compatibility.
3. **CPU for logic, GPU for mass rendering.** Not everything benefits from GPU — see §5.3 for the explicit breakdown.
4. **Incremental, not big-bang.** Each phase delivers something usable and demonstrable (see §22).
5. **Azgaar's `.map` is an interchange format, not the internal model.** Voronia never thinks "in Azgaar terms" internally — only at import/export.
6. **Extensible from day one.** The procedural system is designed to add new generators without touching the core (see §21.4, plugin system).
7. **Everything serializable and versioned.** The `.vorn` format carries a version number from v1 so it can evolve without breaking saved maps.
8. **Strict, synchronized semver.** The whole workspace (8 crates via `version.workspace = true`) shares a single `MAJOR.MINOR.PATCH`. Pre-1.0: `0.x.y`. v1.0 is reached in Phase 9 (§22). Every public release gets a git tag `vX.Y.Z` and a `CHANGELOG.md` entry. The `.vorn` `format_version` is independent of the project semver (it evolves separately, §10).

## 5. System architecture

### 5.1 High-level view

```text
                     AZGAAR .map / JSON export
                              │
                              ▼
                 ┌─────────────────────────┐
                 │   IMPORT / COMPAT LAYER  │
                 │  (regenerates geometry + │
                 │   maps attributes, §3)   │
                 └────────────┬─────────────┘
                              │
                              ▼
                 ┌─────────────────────────┐
                 │    WORLD DATA MODEL      │  (§7)
                 │  grid / pack / cells /   │
                 │  features / rivers /     │
                 │  cultures / states /     │
                 │  burgs / religions /     │
                 │  routes / zones / ice    │
                 └────────────┬─────────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
     SIMULATION ENGINE   EDIT ENGINE     RENDER ENGINE
        (§10)               (§11)           (§9)
              │               │               │
              └───────┬───────┴───────┬───────┘
                      ▼               ▼
                 .vorn (save)   GPU Framebuffer
                      │               │
                      ▼               ▼
                   Disk          Screen (winit/egui)
```

### 5.2 Data flow (mirror of Azgaar's principle, adapted)

```text
Import:   .map/JSON  → import layer → World Data Model
Generate: settings    → simulation engine → World Data Model
Edit:     UI input    → edit engine → World Data Model (controlled mutation)
Render:   World Data Model → render engine → GPU → screen
Save:     World Data Model → serializer → .vorn
Export:   World Data Model → exporters → PNG/SVG/GeoJSON/.map-compatible
```

The renderer **never** writes back to the World Data Model. Editors do, but in a controlled way (undo/redo-able commands).

### 5.3 What benefits from GPU and what does not (technical honesty)

| System | Nature | Benefits from GPU |
|---|---|---|
| Geometry rendering (cells, rivers, borders) | Massively parallel | ✅ Yes, a lot |
| Text/labels | Parallel with more work | ✅ Partially (glyph atlas) |
| Pan/zoom/culling | Parallel | ✅ Yes |
| Heightmap generation (noise) | Parallelizable | ✅ Yes (compute shaders, advanced phase) |
| Delaunay/Voronoi | Sequential/graphs | ❌ Mostly CPU |
| Hydrology (river flow) | Sequential, depends on topological order | ❌ CPU |
| Culture/state/religion expansion | Flood-fill with costs, iterative | ❌ CPU (parallelizable between each other with `rayon`, not within a single flood-fill) |
| Pathfinding (routes) | Graphs (Dijkstra/A*) | ❌ CPU |
| Interactive editing | Low load, interactive | N/A |

Conclusion: the GPU win is mainly in **rendering**, not procedural generation. For generation, the real win comes from **multi-core CPU parallelism** (`rayon`) leveraging the i7-14650HX, not the GPU.

## 6. Tech stack

| Category | Choice | Why |
|---|---|---|
| Language | **Rust** | Memory safety without GC, native performance, strong graphics ecosystem |
| GPU renderer | **wgpu** | Abstracts Vulkan/Metal/DX12, portable, direct Vulkan access on Linux/CachyOS |
| Window/input | **winit** | De facto standard alongside wgpu |
| Immediate-mode UI | **egui** (+ `egui-wgpu`, `egui-winit`) | Integrates directly into wgpu's render pass, ideal for panels/inspectors over the map canvas |
| Graphics math | **glam** | Fast vectors/matrices, standard in Rust gamedev |
| Polygon triangulation | **lyon** | Tessellation of irregular paths/polygons (Voronoi cells) to draw them as triangles |
| Delaunay/Voronoi | Bit-exact port of `delaunator@5.1.0` + Voronoi derivation via circumcenters | Same algorithm family as most generators of this style; must be bit-exact against Azgaar (verified in Phase 0/1) |
| Procedural noise | **noise** | Perlin/Simplex/Worley for heightmap |
| Graphs | **petgraph** | River networks, cell adjacency, route pathfinding |
| Deterministic RNG | **rand + rand_pcg** (or similar seedable) | Total reproducibility with seed |
| Serialization (import) | **serde + serde_json** | Parsing Azgaar's JSON export |
| Serialization (own format) | **bincode** (v1) → evaluate **rkyv** (v2, zero-copy) | bincode is simple and mature; rkyv gives near-instant loads but is more complex — start simple and optimize if needed |
| GPU text | **glyphon** | Modern text rendering over wgpu (burg/state/river labels) |
| CPU parallelism | **rayon** | Parallelizes generation (multiple cultures/states growing at once, per-cell climate, etc.) |
| Images/textures | **image** | Loading external heightmaps, PNG export |
| Errors | **anyhow + thiserror** | Idiomatic error handling |
| Logging | **tracing + tracing-subscriber** | Structured logging |
| CLI | **clap** | Headless tools (batch generation, format conversion without UI) |
| Benchmarking | **criterion** | Detect performance regressions in CI |
| Minimal async | **pollster** | Only to block on wgpu's async initialization |

> Note: no exact crate versions are pinned in this document — use the latest stable ones when starting each phase (`cargo add` resolves this).

### 6.1 Decision: game engine (Bevy) or raw wgpu?

**Recommendation: raw wgpu, not Bevy**, at least for v1. Bevy brings its own ECS, its own abstracted renderer and many conventions that compete with the fine control this project needs (massive 2D rendering of irregular geometry, not a conventional 3D game). It remains a possible re-evaluation in advanced phases if more sophisticated editor tooling is needed.

## 7. World Data Model

Based directly on Azgaar's official data model documentation (wiki `Data-model`), reorganized into idiomatic Rust structs. Azgaar itself describes its current model as "poorly defined and inconsistent" — this is an opportunity to clean up the design (use `enum` instead of magic strings, strong types instead of raw numbers) while keeping the same functional coverage.

### 7.1 Grid vs Pack

- **`Grid`**: initial mesh, jittered square grid points, configurable count (`cells_desired`: default 10,000, minimum 1,000, maximum 100,000 in Azgaar — see §23 for how this informs our performance goals).
- **`Pack`**: mesh derived from `Grid` after "repacking" — optimized for the real landmass (more cell density in relevant areas). Most of the simulation (cultures, states, rivers, etc.) operates on `Pack`, not `Grid`.
- Both meshes are **always regenerated from seed + parameters**, never read directly from the file (see §3).

```rust
struct Grid {
    cells_desired: u32,
    spacing: f32,
    cells_x: u32,
    cells_y: u32,
    points: Vec<[f32; 2]>,
    cells: GridCells,
    vertices: VoronoiVertices,
    features: Vec<Feature>,
}

struct Pack {
    cells: PackCells,
    vertices: VoronoiVertices,
    features: Vec<Feature>,
}

struct VoronoiVertices {
    positions: Vec<[f32; 2]>,
    adjacent_cells: Vec<[i32; 3]>,
    adjacent_vertices: Vec<[i32; 3]>, // -1 if it has no neighbor (border)
}
```

### 7.2 Cells (per-cell attributes — this IS persisted)

### 7.7 Provinces, Religions, Rivers, Markers, Routes, Zones, Ice

All confirmed in Azgaar's real model; listed compactly (full structure analogous to the previous examples — detail 1:1 in Phase 0/1):

- **Province**: subdivision of a state; optional capital, burg list, area, population.
- **Religion**: `Folk | Organized | Heresy | Cult`; expansion `culture` (only within its culture) or `global`; religion tree (origins).
- **River**: `source_cell`, `mouth_cell`, `parent_river`, `basin_id`, `discharge_m3s`, `length_km`, `width_km` — real physical units, not arbitrary.
- **Marker**: point-of-interest pin, icon (emoji/unicode), type, style.
- **Route**: group `roads | trails | searoutes`, control point list, length.
- **Zone**: custom color overlay over a set of cells (to mark special territories, danger zones, etc.).
- **Ice**: `glacier | iceberg` elements, with position and vertices — a dedicated ice system that Azgaar keeps separate from the normal heightmap.

### 7.8 Secondary global data

- **Biomes**: 2D matrix `[temperature][humidity] → biome`, plus per-biome movement cost (used in culture/state expansion) and habitability (used in burg scoring).
- **NameBases**: per-culture name generator — training name list, min/max length, duplicable letters, multi-word name probability. It is a phonetic generation system, not a fixed list.
- **Notes**: legend-like text associated with any entity (burg, state, marker, etc.).

## 8. File formats

### 8.1 Input: Azgaar compatibility

| Format | Description | Priority |
|---|---|---|
| **Legacy `.map`** | Custom text format with concatenated sections + an embedded SVG block. Confirmed by community developers who tried to parse it. | **Priority 1** — officially supported import path in v1 (decision, 25 Jul 2026) |
| **Full JSON export** | Cleaner format, already used by third-party integrations (e.g. the Foundry VTT import module). Without the SVG noise. | Deferred to a later phase — plan B for import if bit-exact replica proves fragile (§3.2) |

In both cases the §3 finding applies: the geometry does not come in the file, it is regenerated.

### 8.2 Own internal format: `.vorn`

- **Binary**, not text — prioritizes load speed over human readability.
- Contains: header with format version + metadata (world name, seed, date, Voronia version that generated it) + the complete serialized `World Data Model` + (optionally) pre-triangulated GPU-ready buffers, to skip tessellation on every load.
- v1 serialization with `bincode`; evaluate migrating to `rkyv` (zero-copy) if load times on large maps are not sufficient.
- Versioned from day 1 (`u16 format_version` in the header) so saved maps can be migrated when the data model evolves.
- **`.vorn` format** (Vorn World File, from "Voronoi"): definitive name of the binary format. Replaces the `.gmap` placeholder used during the design phases. `.vorn` extension — short, original, no collisions with existing formats. The full format name is "Vorn" and it is referred to as "Vorn World File" or "Vorn format".

### 8.3 Export

- **Image** (PNG at arbitrary resolution — a real GPU advantage: exporting high-resolution renders fast, something Azgaar cannot do well because it is tied to the browser DOM/canvas).
- **SVG** (for compatibility with existing community workflows, e.g. later editing in Illustrator/Inkscape).
- **GeoJSON** (for GIS tools like QGIS, same as Azgaar already offers).
- **Azgaar-compatible JSON** (so someone can go back and forth between both tools, if the roadmap justifies it).

## 9. GPU rendering engine

### 9.1 Graphics pipeline

```text
World Data Model
      │
      ▼
Geometry Builder (CPU)
  - Voronoi cell triangulation (lyon)
  - Vertex/index buffer construction per layer
      │
      ▼
Upload to GPU (wgpu buffers)
      │
      ▼
Render Passes (one or more, depending on active layers)
      │
      ▼
Framebuffer → Surface → Screen
```

### 9.2 Layer system (draw order, back to front)

1. Heightmap / base relief
2. Oceans and water bodies
3. Biomes (color by biome)
4. Rivers
5. Ice (glaciers/icebergs)
6. Custom zones (overlays)
7. Cultures (color/hatching)
8. Provinces
9. States / political borders
10. Religions (toggleable mode)
11. Routes (roads, trails, sea routes)
12. Relief icons (forests, mountains — dense pattern by biome)
13. Burgs (city/town/capital icons)
14. Military regiments (toggleable mode)
15. Markers (POIs)
16. Labels (state, burg, river, ocean names)
17. Grid/scale bar, compass, legend (map UI)

Each layer can be toggled individually without regenerating the others — an explicit requirement to avoid Azgaar's performance problem where toggling layers can be costly.

### 9.3 Camera

- **2D orthographic** projection (no 3D perspective — the map is a "sheet", same as Azgaar).
- Pan/zoom = transform the projection matrix (translation + scale). No rotation in v1 (Azgaar does not have it either).
- Zoom with sensible limits; optional spherical projection stays in extensions (§21.6).

### 9.4 Triangulation

Voronoi cells are irregular, potentially non-convex polygons. The GPU only draws triangles, so `lyon` is used to tessellate each cell polygon. The result is cached (not re-tessellated every frame, only when geometry/editing changes).

### 9.5 Picking / selection

Click on the map → convert screen coordinate to world coordinate (inverse of camera matrix) → spatial lookup (quadtree or grid hash, like the `q` Azgaar already uses internally for this) → cell id → resolve to burg/state/culture if applicable.

### 9.6 Text and labels

`glyphon` for GPU text (glyph atlas). Curving state names along their shape (like Azgaar does with its "state labels") is an advanced feature, not blocking for v1 — simple horizontal text first.

### 9.7 LOD and culling

- Frustum culling: do not process/draw cells outside the view.
- LOD by zoom level: at very far zoom, group/simplify geometry (do not draw each individual cell on a 100k-cell map viewed from "the whole continent").

### 9.8 Themes and palettes

- Configurable height palette (Azgaar allows custom color schemes for the heightmap).
- Colorblind-accessible palettes as an option, especially on the biome map.

## 10. Procedural simulation engine

Complete coverage of the systems confirmed to exist in Azgaar today (not hypothetical lists — all documented in its official wiki), to be reimplemented natively. The suggested implementation order goes in §22; here the **functional scope** of each is documented.

### 10.1 Heightmap

- **Template** system (predefined recipes: continents, archipelago, atoll, mediterranean, peninsula, pangea, etc. — confirm the exact set and parameters of each in Phase 0, wiki "Heightmap customization" and "Heightmap template editor").
- Noise combination (Perlin/Simplex via `noise` crate) + manual "blob placement" operations (mountains, depressions) according to the active recipe.
- Support for heightmap imported from an external image (Azgaar allows it — "Heightmap image overlay").

### 10.2 Hydrology

- Precipitation deposited per cell according to the climate system (10.3).
- Water flow following the height gradient, accumulating flux toward the sea — determines which cells have rivers and their width/flow.
- Lake formation in depressions without outlet.
- Confluences where rivers meet (`confluence_flux`).

### 10.3 Climate

- Per-cell temperature (latitude band + height).
- Precipitation (prevailing wind + orographic effect — mountains block humidity).
- Both feed the biome matrix (10.4).

### 10.4 Biomes

- Determined by the `[temperature][humidity] → biome` matrix (confirmed in Azgaar's real model, `biomesMatrix`).
- Each biome has movement cost (affects culture/state expansion) and habitability (affects population/burg score).

### 10.5 Cultures

- "Flood-fill with cost" expansion from center cells, using `expansionism` and biome cost as resistance.
- Inheritance/evolution system (culture tree via `origins`).
- Phonetic namebases per culture (10.9).

### 10.6 States and burgs

- Burg placement by cell `score` (harbor, habitable biomes, proximity to rivers/coast).
- State expansion analogous to cultures, but considering neighboring state borders and capitals.
- Provinces as administrative subdivision within a state.
- Diplomatic system (`diplomacy`, `campaigns`/wars) and military (`Regiment`, war alert) — confirmed as a real, documented system ("Military Forces", "Battle Simulator" in Azgaar's wiki), not a new idea.

### 10.7 Religions

- Types: Folk, Organized, Heresy, Cult.
- Expansion limited to the origin culture or global, depending on type.
- Religion tree (heresies derived from a mother religion).

### 10.8 Routes and economy

- Routes (roads, trails, sea routes) via pathfinding over the cell graph (Dijkstra/A* with `petgraph`), connecting burgs.
- Goods/economy system with "spread functions" (confirmed — Azgaar documents this in its wiki "Goods: spread functions") — goods produced in one place and distributed through trade routes.

### 10.9 Names (namebases)

- Phonetic generator trained with lists of real/fantasy names per culture.
- Rules: min/max length, allowed duplicable letters, probability of collapsing multi-word names into one.
- This is a relatively self-contained system and an ideal candidate to port early and test in isolation (see Phase 0/1).

## 11. Map editing

- **Edit terrain**: height brush, with configurable size/intensity.
- **Edit entities**: move/rename/recolor burgs, states, cultures, religions; merge or split states; lock (`locked`) entities so they are not affected by a partial regeneration (Azgaar already supports this via the `lock` flag on almost all entities — replicated the same way).
- **Manually edit borders**: reassign cells to another state/culture/province by hand.

- **Drawing tools**: brush size, application mode (replace/add/smooth).

## 14. State management, performance and concurrency

- **Structure-of-Arrays (SoA)** for cell attributes (`Vec<u8>`, `Vec<u16>`, etc. indexed by cell id) — the same pattern Azgaar already uses internally with JS `TypedArray`s (`Uint8Array`, `Uint16Array`...), for good cache-locality reasons. The same pattern is kept in Rust.
- **`rayon`** to parallelize independent simulation steps (per-cell climate, simultaneous expansion of multiple cultures before resolving conflicts, etc.).
- The render runs in its own loop (frame loop) decoupled from how long the simulation takes — generating a new world must not freeze the UI (consider running it in a separate thread with progress reported to the UI).

## 15. Persistence, autosave and recovery

Azgaar itself warns its users that **if the `.map` file is lost, there is no way to recover progress** — this is a known, real limitation, not an assumption. Voronia must improve this explicitly:

- Periodic autosave to `.vorn` in a local data location (does not depend on the user remembering to export).
- Versioned saves / snapshot history (at least the last N autosaves, configurable).
- Recovery from unexpected shutdown (detect a previous session not closed properly at startup).

## 16. Testing and QA

- **Unit tests** for each generator with a fixed seed — given the same seed, output must be byte-identical between runs (regression).
- **Import tests**: load real maps exported from Azgaar (several sizes/templates) and verify that the regenerated geometry matches expectations.
- **Visual snapshot testing**: reference renders (PNG) compared by perceptual diff, to detect visual regressions in the renderer.
- **Benchmarks** (`criterion`) on: generation time by map size, `.vorn` load time, pan/zoom FPS on reference maps (10k/50k/100k cells).
- CI runs benchmarks and fails on a performance regression above a defined threshold.

## 21. Extensions beyond Azgaar

This is explicitly what was requested not to leave out: not just matching Azgaar, but **exceeding its current limits**.

### 21.1 No practical scale ceiling
Azgaar limits `cellsDesired` to 100,000 due to browser performance constraints. With native GPU, the goal is to comfortably support that maximum and explore 500k–1M+ cell maps.

### 21.2 Temporal simulation / history
Advance the world by years/centuries generating historical events procedurally (wars, successions, migrations, climate changes), with a navigable timeline ("see the map in year X").

### 21.3 Optional spherical projection
In addition to the "flat sheet" mode (like Azgaar), optionally support a full-planet mode with spherical projection, for worlds that are not just a trimmed continent.

### 21.4 Plugin/scripting system
Extension API (via WASM or an embedded language like Lua/Rhai) so the community can add custom generators (new heightmap templates, new culture types, etc.) without touching the core — something Azgaar does not offer today (it is monolithic).

### 21.5 Export to game engines
Export heightmap + entity data in formats consumable by Godot/Unity/Unreal — a strong differentiator against Azgaar, which is purely cartographic.

### 21.6 LLM-assisted generation integration
Names, descriptions and lore generated/enriched via local LLM. Interesting finding from the research: Azgaar itself already has a dedicated wiki page on **Ollama** integration for text generation, worth reviewing as a reference for what they already tried (see §28).

### 21.7 Headless API / CLI for batch generation
Generate N worlds in batch without UI (`vor-cli`), useful for testing, creating datasets, or headless integrations without opening the graphical app.

### 21.8 Real-time collaboration (long term, optional)
Multi-user editing of the same world — ambitious, explicitly out of v1 scope (§1.4) but documented as a long-term vision.

### Versioning (semver) — rule for every release

- A single version number for the whole workspace (`[workspace.package] version`, inherited by the 8 crates via `version.workspace = true`).
- **Strict SemVer**:
  - Pre-1.0 (`0.x.y`): `x` (minor) = new phases/features or API-breaking changes; `y` (patch) = backward-compatible bugfixes. The `0` major stays until v1.0.
  - Post-1.0: `major` = breaking, `minor` = backward-compatible feature, `patch` = bugfix.
- **On each public release** (convention, in this order): version bump → `CHANGELOG.md` entry (Added/Changed/Fixed/Removed) → commit → git tag `vX.Y.Z` → (eventually) push.
- **Correspondence with the roadmap**: each completed phase that adds visible functionality = minor bump (0.1.0 → 0.2.0 → 0.3.0...). **v1.0.0 = closing of Phase 9**.
- **`VornMetadata.voronia_version`** stores the project semver in each `.vorn` file (for migrations/telemetry); it is informational — real compatibility is governed by `VORN_FORMAT_VERSION` (§10), which evolves independently.
- The handshake test fixture `Sorvik-2026-07-24-23-39.map` (Azgaar 1.138.0) is a map generated under MIT and is committed at `crates/vor-import/tests/reference/` so the tests run for anyone.

## 27. Glossary

- **Voronoi**: partition of the plane into regions based on the nearest "seed" point.
- **Delaunay**: dual triangulation of the Voronoi diagram; each triangle connects 3 neighboring seed points.
- **Heightmap**: terrain elevation map.
- **Biome**: terrain classification by temperature/humidity (forest, desert, tundra, etc.).
- **Burg**: Azgaar's term for a settlement (city/town/capital).
- **Namebase**: set of rules + training data to generate phonetically coherent names per culture.
- **Flux**: accumulated water flow in a cell (used to determine rivers).
- **LOD** (Level of Detail): reducing geometry/render detail by distance/zoom.
- **Tessellation**: decomposing a polygon into triangles so the GPU can draw it.
- **Bind group**: in wgpu, the mechanism to pass data (textures, matrices) to a shader.
- **Render pass**: a drawing pass over a framebuffer.
- **Shader (vertex/fragment)**: program that runs on the GPU; the vertex one transforms positions, the fragment one computes the final color of each pixel.
- **WGSL**: wgpu's native shader language.
- **SoA** (Structure of Arrays): storing each attribute in its own contiguous array (instead of an array of structs) — better CPU cache usage.
- **Zero-copy deserialization**: reading data from disk/memory without copying it into a new structure (what `rkyv` offers).
- **Compute shader**: general-purpose (non-graphic) GPU program, for massively parallel computations.
- **Pole of inaccessibility**: the "deepest" point of a polygon, used by Azgaar as the visual center to place a state/province name.
